# severally の仕組みの詳細

<p><a href="how-it-works.md">English</a> | 日本語</p>

[README](../README.ja.md) に入れていない、相談の進み方の詳細です。どのクライアントから誰に相談するか、相談相手の呼び方、相談の進み方、記録、全員に聞いた相談の答えの
大きさ、相談相手を読み取りだけにとどめる仕組みを書きます。設定のキーはすべて [CONFIG.md](../CONFIG.md) にあります。

機密キーのマスク、置換の観測、推奨案、検証メモに関する変更はv2.10.0から利用できます。
旧履歴も読めます。項目がない場合は、不明または未表明として扱います。

## どのクライアントから誰に相談するか

```mermaid
flowchart TB
  you(["あなた"]) <-->|"↓ 作業の指示<br>↑ 確かめた結果と、決めてほしいこと"| lead["主担当<br>作業中のエージェント"]
  lead <-->|"↓ ブリーフとコードの写し<br>↑ 相談相手ごとの答え"| srv["severally サーバ"]
  srv <--> c1 & c2 & c3 & c4
  subgraph cs["相談相手（読み取り専用の新しいセッション）"]
    c1["Codex"]
    c2["Claude Code"]
    c3["Antigravity"]
    c4["OpenCode"]
  end
```

主担当はあなたといっしょに作業しているエージェントです。*ブリーフ*（質問と、その前提になる事実）を書き、関係する
コードの読み取り専用の写しを添えて相談します。答えが返ったら指摘を自分で確かめ、あなたが決めることだけを
訊きます。ふだんの相談で主担当がするのは、相談を始める、答えを待つ、確かめた指摘を 1 つ記録する、の 3 つです。

相談相手はこの質問のためだけに起動した、その CLI の新しいセッションです。会話履歴は自動では引き継ぎません。
サーバは主担当が書き込んだ内容を含むブリーフと、明示して公開したファイルを送ります。
CLIによってはそのほかのファイルも読めます。severally のサーバはどの相談相手にも同じブリーフを送り、答えを相談相手ごとに返します。答えをまとめたり、どれが正しいかを判定したりはしません。

相談相手が何を読めて何ができるかは、[相談相手が読めるものとできること](../README.ja.md#相談相手が読めるものとできること)に書いています。


どのクライアントから使っても、ほかの 3 つの CLI と、自分の CLI の新しいセッションに相談できます。サーバが起動する
コマンドは次のとおりです。同時に動かせる相談相手は既定ではすべてのセッションを合わせて 9 人までです。

```text
Claude Code ──(skill)──> severally server ──> codex exec | agy | opencode run | claude -p  (fresh session)
Codex       ──(skill)──> severally server ──> claude -p  | agy | opencode run | codex exec (fresh session)
Antigravity ──(skill)──> severally server ──> codex exec | claude -p | opencode run | agy  (fresh session)
OpenCode    ──(skill)──> severally server ──> codex exec | claude -p | agy | opencode run (fresh session)
```


## 相談相手の呼び方

- 相談相手は 1 つの CLI と 1 つのモデルの組なので、CLI の名前（「Codex に聞いて」「Gemini に聞いて」）でも、モデルの名前
  （「Claude Opus に聞いて」「DeepSeek に聞いて」）でも呼べます。
- 運用者が設定すれば、OpenCode で動く GLM と DeepSeek のように、1 つの CLI に相談相手を何人でも置けます
  （[CONFIG.md](../CONFIG.md) を参照）。OpenCode を通せば、OpenAI 互換のサーバ（ollama、LM Studio、vLLM）で動くローカルの
  モデルや、OpenRouter のモデル（Qwen と Kimi で確かめた）も相談相手にできます。
- 名前が 2 人以上に当てはまるときは、上位のモデルか、新しいバージョンのモデルに聞きます。決められなければ、
  主担当がどの相談相手のことかをあなたに尋ねます。
- 全員に聞くときの使用量は相談相手 1 人につき 1 回分で、既定の設定（CLI ごとに 1 人）なら 4 人分です。質問が小さければ、
  主担当が人数を減らすこともあります。
- 自分の CLI からの答えには、どのモデルが答えた場合でも「同じ系統（same lineage）」の注記が付くので、ほかのベンダーの
  答えと見分けられます。

## 相談の進み方

前提を含む `question` だけで、一般的な `explore` の相談を始められます。`context.facts` は任意で、質問の前提を重ねて書く必要はありません。
コードの相談にはファイルか差分を添えます。`review` の計画、`debate` の計画と反対意見は引き続き必要です。

- 相談を始めても、主担当は相談している計画そのものは進めません。
- 共有枠が足りない場合、モデルを呼ぶ前に `concurrency_limit` を返します。`details` には要求・使用・空き・不足の枠数、
  上限、その主担当が既に扱っている占有ジョブ ID、他セッションの占有件数と再試行の案内が入ります。
  主担当は既知のジョブの終了を待ち、他セッションしか占有していなければ案内された間隔を置いて、同じ依頼を最大2回・
  合計60秒以内で再送できます。再確認の間隔は開始時刻の保証ではありません。要求数が上限自体を超える場合は再試行しません。
  開始済みの依頼を再送せず、無関係な相談の中止や上限の回避も行いません。
- 一時的な失敗（`rate_limited`、`cli_error`）は、少し待ってから、同じ時間の枠の中で、同じ相談相手とモデルで最大 2 回
  やり直します。それまでの失敗は `retries` に残ります。
- 相談相手のモデルがアカウントの使用枠を使い切ったとき（`usage_limit`）は、設定に `fallback_model` があれば、その
  モデルで 1 回だけやり直します。答えには代わりのモデルが答えたことが書かれ、`model` には実際に答えたモデルが入ります。
- 時間切れになったときは、相談相手がそこまでに書いていた内容の末尾を、途中までのものという印を付けて失敗の隣に
  残します。これは読む材料として残すもので、答えとしては扱いません。
- 履歴に保存された相談の結果はサーバを再起動したあとも、同じマシンで動くほかの severally のプロセスからも読めます。ほかのプロセスで
  実行中のものは実行中と返ります。終わる前にサーバがクラッシュや強制終了で止まったものは `interrupted` として返ります。
  サーバがふつうに終了したときは、実行中の相談を取り消しとして記録します。
- 回答の保存に失敗しても、`consult_get` は回答と `history_warning` を返します。`stage` は回答ファイルと索引のどちらで失敗したかを示し、
  `round_saved`、`index_saved`、`recovery_saved` は各記録を保存できたかを示します。保存先の権限や空き容量を直してから同じジョブを取得すると、
  相談相手を呼び直さずに保存を再試行します。復旧用の完了記録が残っていれば、別のサーバでも保存を再試行できます。
  この記録を実行中や `interrupted` として扱うことはありません。復旧用の記録も保存できなかった場合は、実行元のサーバが再起動する前か、
  回答がメモリから消える前に同じジョブを取得してください。グループの保存失敗は開始時と取得時に別途知らせます。
  保存先を直して実行元のサーバからグループを取得し直してください。グループが失われた場合に備えて、保存済みの回答を個別に取得できる各メンバーのジョブ ID も控えます。
- 子プロセスの起動後、`consult_get` は `progress_observation` に観測時刻、経過時間、認識したイベントの数、試行番号、期限を返します。
  別プロセスからも同じ保存済みの観測を読めます。イベントがない場合は活動未観測と示し、停止や推論中とは判断しません。
  イベント本文やコマンドはこの観測に保存しません。
- ほかの severally のプロセスから `consult_cancel` を呼ぶと、相談を実行しているプロセスへの取り消しの依頼を
  残します。実行しているプロセスは 1 秒ごとにそれを確かめ、相談を止めます。
- 主担当が自分では実行できない確認（ほかの人の答えが要るものなど）は、理由をつけてあなたに返します。
- **あとで判断の理由を説明する必要がある決定**（インターフェース、移行、セキュリティ、並行処理）では、主担当は
  自分から、またはあなたに頼まれて、手順を足します。質問と成功の条件をはっきりさせ、課された制約と自分の仮定を
  分け、相談相手が何と言いそうかを先に書き留めます。こうしておくと、どこで予想が外れたかが記録に残ります。
  記録は Markdown のファイルとして、コードの隣か、リポジトリが判断の記録を置いている場所に置きます。このファイルは
  ふつうの変更なので、ほかの変更と同じようにレビューします。
- モードは計画のない依頼が `explore`、計画のある依頼が `review`、計画と反対の主張がある依頼が `debate` になります。
  計画を含んだ最初の `explore` の依頼は、サーバが受け付けません。追加の質問は元の相談のモードを引き継ぎます。
  主担当が渡し直さない限り、ほかに渡したもの（相談相手、`network`、目的、制約、成功条件、事実、計画、反対の主張、
  資料）も引き継ぎ、新しいブリーフに書き直して載せます。
  追加の質問の上限は設定ファイルの `server.max_rounds` で変えられます。

追加相談では CLI の新しいセッションを起動し、保存した質問・回答・確認記録からブリーフを組み立てます。
CLI 自身のセッションを再開する方式ではありません。前提が変わった場合は、変更した前提、維持する助言と撤回する助言、
具体的な変更箇所と確認方法を示します。

## 記録

`limits.network` はサーバの既定値です。各回の設定はジョブやグループの `network` に示します。
ジョブの `boundary.network` には起動時に適用した設定を残します。
たとえば依頼で `network: "off"` を指定すると、`limits.network` が `"on"` でも、その回は Web を閲覧できません。
設定値の表示だけで、実際に試みた操作が拒否されたとは確認できません。
Windows 10 以降では、CLI を起動時に Job Object へ登録します。Job を閉じると、CLI が先に終了した場合も、
別のプロセスグループで起動した子を含め、通常の子孫プロセスを止めます。Job のハンドルは子に継承しません。
中止は生存中の起動用プロセスを対象とし、別のプロセスに再利用されたかもしれない CLI の PID へ停止要求を送りません。
起動には Windows 標準の PowerShell 5.1 と .NET の `Add-Type` を使います。ポリシーでコンパイルやネイティブ API が
禁止されている環境では起動できず、Job を使わない方式への切替もしません。失敗理由は stderr に表示しますが、
起動処理の失敗と CLI 自体の失敗を結果から区別する機能には制限があります。
Windows 10.0.26300.9711・Node 22.16.0・PowerShell 5.1 の実機試験では、親の先行終了、中止、タイムアウト、
日本語を含む標準入力・引数、cmd の転送、終了コードを確認しています。対象は `test/windows-job.test.mjs` と
`test/windows.test.mjs` です。変更前には、別のプロセスグループで起動した子が親の終了後も残ることを再現しました。
WMI などのサービス経由で起動したプロセス、外部での Job 設定、サーバの異常終了の全経路は保証の対象外です。
中止要求の完了だけでは、子孫の終了を確認したことにはなりません。

- 往復ごとに 1 つのファイルがあり、判定には、それが判断に与えた影響も残ります。判定の意味は、`confirmed` が
  「記録した検証範囲で成り立った」、`refuted` が「その検証では成り立たなかった」、`not_applicable` が「一般には正しいが、このコードには当てはまらない」、`unverifiable` が
  「主担当が手の届く範囲では決着できない」、`unverified` が「確かめていない（理由つき）」です。
- 全員に聞いた相談の判定は、`consult_record` の 1 回の呼び出し（`records`）で全員分を記録できます。job や指摘の id が
  1 つでも違えば何も書きません。判定を保存できなかったときは、そのことを応答で知らせます。
- 一部だけ確かめた指摘は `unverified` のまま、`note` に確認範囲を残します。`effect` は採否や判断への影響であり、
  検証結果とは分けます。キャッシュキーの衝突を再現しただけでは、認証迂回まで確認したことにはなりません。
  衝突の結果を記録し、実際の認証経路を確かめるまでは、より広い主張を未検証として残します。
- 新しく `consult_record` に渡す `note` は、確認した入力・環境・結果・限界のうち、追加相談で共有できる要約です。
  サーバはその要約を最大 400 文字の `followup_note` として保存し、短縮した場合は明示して、追加相談へ渡します。
  `followup_note` のない旧履歴の注記は、明示的に記録し直すまで手元に残り、追加相談には渡しません。
- 記録にはどのモデルがどのモデルに聞いたかと、相談をあなたが頼んだのかも残ります。
- 最近の相談の一覧（`consult_list`）では、このセッションで各 CLI が報告したトークン数と費用を、相談相手ごとに合計して
  示します（`usage_totals`。自動の再試行の分も含む）。CLI が報告しない値は、0 とは数えずに `not_reported` に名前を
  挙げます。取り消した相談と期限切れの相談は使用量が残らないので、`unreported` にその数を示します（合計が、動いた
  分すべてには見えないようにするため）。

Markdown 書き出しの先頭には検証済みの指摘をまとめます。相談相手、実際のモデル、ジョブと指摘の ID、判定、
判断への影響、確認した根拠が並び、指摘の全文へリンクします。未記録・未検証・確認不能の指摘は検証済みと分けて
件数を示します。`confirmed` は採用したという意味ではありません。各回答と記録の全文は後に残し、サーバが意味を
統合したり採否を推定したりすることはありません。
再実行の書き出しには元の失敗とジョブ・相談の ID も示し、保存されている以前の失敗・文脈の記録を一度ずつ添えます。
失われた元の記録はその ID を明示します。添付するのは後日の検証結果を含む現在の記録であり、当時送った文脈は
短縮されていた場合があります。

短い報告でも、判断を左右する指摘から主担当の検証までを追えるようにします。

```text
指摘: 再試行による増幅（job_… / f1）
相談相手: Codex、gpt-6.1-sol。結論: do_not_proceed
推奨: リリース前に操作 ID を保持する。
根拠: 呼出元は取消後も同じ操作を送り直せる。
主担当の確認: 取消しの回帰テストで 2 回目の送信を再現した。
採否と影響: 呼出元が操作 ID を保持するまでリリースを見送る。
未検証: 本番の負荷。負荷試験の環境がない。
```

コードの相談ではimport と実際の呼出箇所を読み、差分に加えて必要な呼出元・テスト・設定を選びます。
差分に含まれないファイルは `expose_paths` で足します。公開ファイル数と除外・削除を確認し、足りない前提は不明点として
残します。判断に必要な資料が足りなければ、実装・呼出元・設定・テストから必要なものだけを選び、1 回補います。
それでも足りなければ、判断への影響を明記します。ツール入力にファイル名が現れても、関連する動作を読み取って理解した証明にはなりません。

## 全員に聞いた相談の答えの大きさ

全員に聞いた相談の標準応答には、JSON の字下げを含めて 19,500 文字の予算があります。
応答サイズの試験では、最大 9 人・回答の各長さ上限・エスケープが必要な文字・一部の相手の失敗を確認しています。
比較では各相談相手の実際の回答モデル、立場、具体的な推奨案 `recommendation` を並べ、そのあとに
`decision_changers` と `unknowns` を示します。同じ立場でも、推奨する選択肢は異なる場合があります。
`recommendation` は立場と別の項目です。旧履歴にない場合は `null`（未表明）とし、要約から推定しません。
応答には要約と、指摘の id・重大度・内容・根拠も含みます。ほかの一覧よりも指摘に
多くの表示量を割り当てます。`next_checks` には検証内容と `method`・`expected_signal` を同じ文字数予算の範囲で含めます。
短縮した文は `truncated`、入りきらなかった項目の数は `omitted` で示します。
サーバが指摘を順位付けしたり、書き直したりすることはありません。

グループの待機は新たなメンバーが終了した時点で返るので、ほかの相手を待ちながら届いた回答を検証できます。
次の待機は別のメンバーの終了か待機上限まで続き、取得済みの回答だけを理由に即時応答を繰り返しません。
別サーバからは履歴を 1 秒間隔で読み直して終了を確認します。
グループの `status: done` は、取得できたメンバーが全員終了したことを示し、全員の成功は意味しません。
`member_counts` は成功（`completed`）、失敗（`failed`）、取消（`cancelled`）、実行待ち・実行中・取消処理中（`pending`）、
履歴を取得できないメンバー（`missing`）の数を示します。各メンバーの状態も確認し、失敗や欠落を報告してください。

主担当は全文が表示された根拠を読み、判断を左右する主張を自分で確かめます。欠落・短縮された詳細は
`consult_get({ job_id, ids: ["f2", "f5"] })` で、その指摘の全文を根拠付きで取れます。
各相談相手の全文は `consult_get({ job_id })` で取れます。`consult_get({ group_id, detail: "full" })` は、ブリーフと質問を
省略せずに返します。回答に割り当てる 19,500 文字の予算は変わりません。
保存される回答の内容は省略しません。

## 相談相手を読み取りだけにとどめる仕組み

要約と CLI ごとの表はREADME の[相談相手が読めるものとできること](../README.ja.md#相談相手が読めるものとできること)にあります。
ここには、それをどう守らせているかを書きます。

README の表で「拒否」とした秘密のパスは、`~/.ssh`、クラウドやパッケージレジストリの鍵、ほかのコーディングツールのセッション、
severally 自身の履歴と、ほかの相談相手のサンドボックスのホーム、そしてどこにあっても `.env`、`.npmrc`、`id_rsa` のような
ファイルです。

Codex はパスを拒否しますが、名前では拒否できません。「どこにある `.env` でも」を指定できないため、リポジトリの
`.env` は読めます。既定の `~/.codex` や移動した `CODEX_HOME` などの資格情報ディレクトリは、実行ファイルが外にあれば
全体を拒否します。保護対象の中に実行ファイルがある構成は、枠の確保やモデル呼出しの前に
`unsafe_codex_placement` で拒否します。CLI の権限生成にはその配置で実行ファイルの例外が必要になるため、
資格情報ルートの外へ導入してください。
既存のリンクで指定した保護ルートは実パスへ解決して一度だけ登録し、Linux で同じ場所を別名でもマウントすることによる
起動失敗を避けています。

Windows の Codex は、存在しない拒否パスをディレクトリとして作ってから拒否し、その拒否を実行後も残します。そのため
Windows では起動時に存在する保護パスだけを渡し、無い `~/.npmrc` や `~/.git-credentials` がディレクトリにならないように
しています。起動後に作られた保護ファイルは、そこでは拒否されません。拒否している保護ルート内配置で項目ごとに拒否すると、
Codex 自身の daemon 用ディレクトリにも拒否が付き、アクセス制御の項目が 1 件であることを求める検証に落ちて、通常の `codex`
が起動しなくなりました。どちらも Codex のソースと利用者の報告に基づくもので、severally は Windows で実行していません。

Linux では、ホストが実行中の保護ファイルを rename で置換すると、ファイル単位の拒否が効かなくなることがあります。
2026-10-24 の Codex 0.164.0 の合成試験では、変更前の既定のホームで、認証ファイルの置換後と新しい隣接ファイルの
読取りを再現しました。2026-10-26 に修正後のアダプターで試し、実行ファイルが外にある既定ホームでは、直接指定とリンク指定の
両方で既存・置換後・新規のファイルを拒否し、公開ファイルは読めることを確認しました。認証済みの相談も完了しました
（設定・起動モデルは `gpt-6.1-sol`、effort は `low`。プロバイダーの実効モデルと effort は独立には観測していません）。
`~/.claude.json` など、個別に保護するファイルの rename 置換は未解決です。CLI のサンドボックスの制約であり、
`expose_paths` の伏せ字処理では解消しません。

2026-10-27（JST）に Linux / Codex 0.164.0 で合成データを使い、残る 3 条件を再現しました。個別に拒否したファイルの
rename 置換、実行ファイルを含む保護ルートへの新規ファイル追加、起動後の旧形式 `jobs/<id>/home` 作成です。
いずれも作成・置換後のファイルを読めました。既存の旧形式ホームは拒否され、公開ファイルは読めました。
実行ファイルを資格情報ルートの外へ置いた場合、そのルート内では置換後も新規作成後も拒否が続きました。
ルート全体を拒否して実行ファイルのディレクトリだけ読取りを許す設定も試しましたが、実行ファイルも拒否されました。
この設定では項目ごとの列挙を置き換えられません。実行ファイルは資格情報ルートの外に置き、1.7 より前の severally は
現在の相談と並行実行しないでください。今回の試験はモデルを呼び出しておらず、認証済み相談の再試行もしていません。
macOS・Windows でのこれらの条件は未検証です。

OpenCode には保護パスの絶対パスと、Location・作業ツリーからの相対パスを拒否する規則を渡します。
`grep` と `glob` は返すファイルごとに規則を確認しないため無効にしています。OpenCode 2.0.24 の組込みの読み取り判定は
パスの文字列を使います。別名経由にも対処するため、severally は合成 HOME に、外部パッケージに依存しない専用プラグインを
配置します。[ツール実行前のフック](https://opencode.ai/v2/docs/build/plugins#tools)で、`read` のたびに指定パスと実パスを
共通の保護ルート・ファイル名と照合し、解決できないパスも拒否します。許可したパスは実パスに直して CLI へ渡します。
保護ルートも読取りのたびに解決し、起動後に作られたルートや、リンク先が変わったルートの現在の実体を検査に含めます。
V1 の `server()` と V2 の `setup()` に対応するフックを持ち、ユーザーのプラグインは引き継ぎません。
フックの検査と CLI がファイルを開く操作は別なので、その間に実パスのファイルや祖先ディレクトリが差し替わる場合は保護しません。

2026-10-26 の Linux・OpenCode 2.0.24 の合成試験では、直接指定・相対指定・リンク・リンク差替え後の読取りを拒否し、
ローカルの模擬モデルへ合成秘密が届かないことを確認しました。公開ファイルの読取りは成功しました。
試験は `network: "off"` で行いましたが、この設定だけでは読取り結果のモデルへの送信は止まりません。
V1 のフックと生成バンドルは単体テストで確認しています。実際の V1 CLI での読込みと、macOS・Windows での強制結果は未検証です。
この保護には、専用プラグインを読み込む CLI が必要です。

サーバの環境変数と `clis.<cli>.env` にある既知の絶対パスも保護します。対象は `CODEX_HOME`、`CLAUDE_CONFIG_DIR`、
`XDG_CONFIG_HOME`・`XDG_DATA_HOME` 内の OpenCode、`GOOGLE_APPLICATION_CREDENTIALS`、`HOME` 配下の保護対象
（Windows では `USERPROFILE` も）です。実際の severally 設定ファイル、`SEVERALLY_AGY_CRED_HOME` 内の `.gemini`、
`SEVERALLY_OPENCODE_CRED_HOME` 内の `.local/share/opencode` も含めます。設定したシンボリックリンクの既存の実体も
対象ですが、CLI やプラグインの引数で指定した任意の場所、相対パスと、上記の検査で扱う範囲を超えた新しい別名や実行中の変更は保証しません。
資格情報は絶対パスで指定し、実行ファイルの除外項目から分けてください。こうした読み取りの抜けが問題になる場合は、
ほかの秘密情報を置かない専用の OS アカウントで実行してください。

`expose_paths` と `expose_diff` は保護対象として認識したパスとその配下を除外します。ハードリンクが複数ある
ファイルも除外します。ファイルを直接指定した場合はエラーにし、ディレクトリや差分の中で見つけた場合は除外理由を
報告します。公開したいファイルは独立したコピーを用意してください。リンク数に加え、ファイルの同一性、サイズ、
更新時刻と実パスを開く前後・読む前後に比較し、差替えや変更を検出した場合は公開を拒否します。
ツリー全体の原子的スナップショットや、すべての同時変更・不正確なメタデータに対する保護は保証しません。
このコピー時の検査は、相談相手が直接読める範囲を制限するものではありません。
送るブリーフと返ってくる答えでは、認証情報を伏せ字にします。
相談相手が自分で開いたファイルは、そのまま読まれます。
サーバの環境変数にあるほかのサービスの認証情報（`AWS_*`、`GITHUB_TOKEN`、`SSH_AUTH_SOCK`、名前が `_TOKEN`・`_SECRET`・
`_API_KEY` などで終わるもの）は、相談相手に渡しません。認証情報のうち渡るのは、その相談相手のベンダーの鍵、`clis.<cli>.env` に
書いたもの、OpenCode では `clis.opencode.provider` の `{env:NAME}` が名指しする変数です。

機密名は `api_key`、`password`、`access_token`、`client_secret` などで、大文字小文字を区別せず、アンダースコア区切りの
接頭辞も認識します。全大文字の独自の `*_KEY` も保守的に機密扱いします。構造化オブジェクトでは該当するキーの値全体を
`[REDACTED]` に置換します。短い文字列、数値、null、コード参照、配列、オブジェクトでも同じです。その他の配列・オブジェクトは
入力を変更せずに再帰処理し、`primary_key` や `sort_key` などの通常の識別子を保持します。
文字列の代入式では従来の最小文字数とコード参照の除外条件を維持します。そのため、コードを文字列として渡した
`password: true` は残る場合がありますが、構造化データの `{ password: true }` はマスクします。camelCase とハイフン区切りの
名前全般には対応していません。すべての秘密を検出する保証はなく、同じマーカーに置換された値が元も同じだったとは限りません。

`quality.redaction` は `files`・`brief`・`result` の各段階で置換を観察したかを示します。`true` は置換あり、
`false` は置換を観察しなかったこと、`null` は不明を表し、旧履歴も不明として扱います。
公開ファイルのマニフェストにも `redacted` があり、比較表示と Markdown 書き出しにも観察結果が残ります。
`files` はファイルコピーと差分準備での置換、`brief` はその後に組み立てた本文での置換を観察します。
安全な反例には、フィールドの有無・削除・型・構造の違いと、手元での再現結果を使います。
マスクした秘密を復元したり、同じマーカーを元の値が等しかった証拠にしたりしません。

実行可能な反例では、公開してよいフィールド名と、明らかに架空の値を別の変数にします。
秘密らしい名前へのリテラル代入は、マスクで値を置換したあとに構文が壊れる場合があります。
たとえば、リポジトリのルートで次のように確認できます。値そのものは出力せず、真偽値や assertion で結果を確かめます。

```js
import assert from 'node:assert/strict';
import { redact } from './src/redact.mjs';

const field = 'api_key';
const sample = 'SYNTHETIC_ONLY';
const input = Object.fromEntries([[field, sample]]);
const output = redact(input);
assert.equal(Object.hasOwn(output, field), true);
assert.equal(Object.is(output[field], sample), false);
```

`node scripts/live-check.mjs --target <名前> --mode sandbox` は、作業ディレクトリの内側と外側へのファイルの書き込みと、
コマンドの実行を相談相手に試させ、ディスクを確かめます。2026-10-18 の実行では、Codex・Claude Code・Antigravity のどれも
何も書けませんでした。Antigravity はフックが 3 つとも拒否し、Claude Code には書き込みとシェルの道具がそもそもありませんでした。
Codex は試すこと自体を断ったので、権限プロファイルの効き目はこの実行では確かめられていません。

Antigravity にはツールを制限するフラグが無いので、Antigravity の相談相手のツール呼び出しは、すべてフックを通ります。
フックは読み取りと Web を許し、それ以外は、後のバージョンで足されたツールも含めてすべて拒否します。Codex は既定では
有効になっている子エージェントのツールを切って起動し、`-s read-only` の代わりに権限プロファイルを使います。
このプロファイルにより、ディスクは読み取り専用になり、シェルからはネットワークに出られず、秘密のパスは読めなくなります。

どの答えにもその相談相手をどう起動したかを示す `boundary` の記録（何を読めたか、シェル、Web の有無、秘密のパスを
拒否したか）と、`tool_calls` が付きます。`tool_calls` は、その相談相手が実際に呼んだツールで、CLI 自身のイベントの
記録から数えます（Claude Code はツール呼び出しを流さないので、`tool_calls` がありません）。Codex・Antigravity・OpenCode には
`tool_inputs` も付き、その呼び出しに何を渡したかが分かります。Codex が実行したシェルのコマンド（30 件まで。秘密は
伏せ字にし、1 件を 200 文字で切ります。出力は残しません）か、Antigravity と OpenCode の
ファイルツールが受け取ったパスや検索パターンです。渡した
ファイルのうち何件が呼び出しに現れたかも数えます。呼び出しに名前が出ても、そのファイルを読んだ証拠にはならず、
名前が出ないファイルを飛ばしたとも限りません。グループの表示には件数（`exposed_files_in_tool_inputs`）だけを出します。

`npm run doctor` は、あなたのマシンにある CLI を相手に、この境界を確かめます。それぞれの相談相手に、次のことを
試させます。

- ファイルを書く
- ファイルを書くコマンドを実行する
- カナリアの `.env` と、保護したディレクトリの下に置いたカナリアを、読んでよい対照のファイルといっしょに読む
- 子エージェントを起動する

結果は相談相手の自己申告ではなく、外から読み取ります。確かめるのは、ファイルができていないこと、対照の言葉は
返ってきたのにカナリアの言葉は返ってこなかったこと、`tool_calls` に子エージェントのツールが出ていないことです。ただし、ファイルが
無いことやカナリアが返らないことが示すのは、何も通らなかったことです。試したうえで拒否されたことまでは示しません
（相談相手が試すこと自体を断る場合があります）。そこで Codex では、doctor が同じプロファイルで `codex sandbox` も
実行し、保護したカナリアの読み取りが Permission denied になることを確かめます。Claude Code の子エージェントの行は、
渡したツールの一覧を示すことしかできません。確かめられなかった行があると、doctor は失敗として終わります。これまでに
実行したのは Linux だけで、実行には実際の使用量がかかります。

質問がリポジトリのコードについてなら、主担当は最初の依頼で、関係するファイルを絶対パスで指定して渡します
（`expose_paths`）。テストの出力やログのようにファイルでないものはブリーフに入れます。ブリーフに貼った抜粋は
ファイルの代わりではなく、ファイルに添えるものです。指定したファイルとディレクトリは、読み取り専用で相談相手の作業
ディレクトリ（`./workspace` の下）に写します。上限は合わせて 20 項目、500 ファイル、5 MB です。git の作業ツリーの中のディレクトリは、
git が管理するファイル（追跡しているものと、`.gitignore` で外していない未追跡のもの）だけを写すので、リポジトリのルートも
上限に収まります。git の外では `.git` と `node_modules` を飛ばします。シンボリックリンクは
たどらずに飛ばし、テキストファイルはブリーフと同じように認証情報を伏せ字にして、バイナリファイルはそのまま写します。

変更中のコードを見せるときは、代わりにリポジトリのパスを `expose_diff` で渡せます。差分（`HEAD`、または `base` に
指定したリビジョンとの差）は、ブリーフの上限（最大 20,000 文字）に収まるよう切り詰めてブリーフに入り、差分が触る
ファイルは未追跡のものも含めて、`./workspace/repo/` の下にリポジトリと同じパスで写します。保護したファイルはどちらからも外し、git は外部の diff・textconv と fsmonitor を
止めて動かします。リポジトリの場所は送りません。写しは 1 回の依頼につき 1 度だけ作るので、同時に聞いた相談相手は
全員が同じバイト列を読みます。履歴にはその SHA-256 を残します。

写しはジョブとともに消え、履歴にはファイルの中身ではなく、どのパスを見せたかだけが残ります。差分はブリーフの一部なので、
ほかの部分と同じく伏せ字にしたうえで、ブリーフとともに残ります。その相談の間、Claude Code の相談相手は
写しだけを読みます。ほかの 3 人はディスクのほかの場所も読めます。

追加の質問は新しい作業ディレクトリで始まり、前の回に見せたものを、主担当が足したパスと一緒に今の内容で写し直します。
前の回から変わったかどうかは、項目ごとに SHA-256 で示します。ディレクトリは並べ直すので、あとから増えたファイルも写ります。
無くなったパスは飛ばし、その名前を挙げます。前の回の `expose_diff` は差分を取り直さず、差分が触ったファイルだけを写し直します。

前の回のファイルを渡さないときは、主担当が `expose_from_parent: false` を付けます。相談相手の名前がいまは別の CLI やモデルを
指しているときは、`true` を付けない限り何も写し直しません。

全員に聞いた相談への追加の質問（`followup_to` に `group_id` を渡す）は、全員に同じ新しい質問を送ります。それぞれの
相談相手は自分のやりとりの最新の答えから続けるので、ブリーフにはその相談相手自身の前の回が入ります。まだ動いている
相談相手、答えの無い相談相手、回数を使い切った相談相手には送らず、`consult_start` の応答の `skipped` に理由とともに挙げます。

## 使い方の例

severally を使うと、エージェントの仕事の進め方がどう変わるかを、1 つの場面で示します。エージェントが変更を
思いつき、あなたに承認を求める前に、相談相手の意見を聞く場面です。

例に使うのは、小さなネットショップの API です。商品ページを返す `GET /products/:id` が遅く、約 800 ms
かかっています。この API は商品に在庫とレビューを結合して読み込んでいます。また、商品の価格は会員の
ランクで変わり、ゴールド会員には 10% の割引が付きます。

Claude Code で動くエージェントは、「レスポンスをメモリ上の Map に 5 分間保持する」というよくある修正を
考えました。あなたに「進めてよいですか」と尋ねる前に、この計画を 3 人の相談相手に見せます。Codex、
Antigravity、新しい Claude Code のセッション（エージェント自身の CLI の新しいセッションで、会話は
引き継がない）です。計画と一緒に、関係するコードの読み取り専用の写しも渡します。答えは相談相手ごとに、
横に並んで返ってきます（サンプルの API に対する実際の実行結果の抜粋を訳したもの）。

```text
codex        do_not_proceed  価格は会員のランクで変わるので、商品 ID だけで保持すると、最初に来た人の
                             価格が全員に返る。結合で在庫数が水増しされている。4 つのワーカーが別々に保持するので、
                             注文で在庫が変わっても古い値が消えない
claude-code  do_not_proceed  最初にキャッシュに入った人の価格が、5 分間ほかの全員に返る。4 つのワーカーがそれぞれ
                             保持するので、注文のあとも在庫が古いまま残る。結合の不具合も先に直す
antigravity  alternative     会員の割引がほかの利用者に漏れる。800 ms の原因は在庫とレビューの結合で、在庫数も
                             狂わせている。クエリを書き直せば、キャッシュなしで十分に速くなる見込みがある
```

どの答えも結論から始まります。結論は `proceed`（進めてよい）、`do_not_proceed`（進めない）、`alternative`
（代わりに別のことをする）、`undetermined`（決められない）のどれかです。3 人は価格の漏れ、在庫の水増し、
ワーカーごとのキャッシュという同じ問題を、それぞれ独立に見つけました。違うのはその先です。Codex と
Claude Code は、クエリを直したうえで、利用者によらない部分だけをキャッシュするよう勧めています。
Antigravity は、クエリを直せばキャッシュ自体が要らないかもしれないと言っています。答えを 1 つにまとめると、
この違いは埋もれてしまいます。

相談したエージェント（以下、*主担当*）は、指摘を読んだあと、自分のリポジトリで確かめます。2 つの指摘の
うち、1 つはそのとおりに再現しました。もう 1 つは、今はまだ起きていないと分かり、対応が変わりました。

```text
指摘     クエリが在庫とレビューを一緒に結合しているので、在庫数がレビューの数だけ掛け算される
  確認   テスト用のデータベースでクエリを実行: 在庫 5 個、レビュー 4 件 -> 在庫数が 20 になる
  判断   キャッシュより先に、クエリを直す

指摘     ゴールド会員の 10% 割引がゲストにも返る
  確認   ログインの仕組みはまだ組み込まれていないので、今は全員が基本価格になる。
         漏れはログインを足した日から始まる
  判断   キャッシュするのは利用者によらない商品の情報だけにし、価格はリクエストごとに計算する
```

あなたに返ってくるのは「反対 2、代案 1」という票の数ではありません。何を確かめたか、主担当が何を勧めるか、
まだ何を確かめていないかです。この例でまだ確かめていないのは、直したクエリがキャッシュなしで十分に速いか
（本番に近いデータが要る）と、注文のあと在庫の表示がどれだけ古くてもよいか（あなたが決めること）です。
判断はあなたがします。確かめた結果は指摘の隣に残り、Markdown としてリポジトリに書き出せます
（[履歴と記録](../README.ja.md#追加質問と履歴)を参照）。

## おすすめの構成

各ベンダーの最上位のモデルを相談相手に登録しておき、ふだんの作業は Claude Code の Sonnet のような安価なモデルで
進める、という使い方です。コードの編集、テストの実行、検索など、作業の大半は安価なモデルで足ります。
設計の選択や巻き戻しにくい変更など、判断を誤ったときの損が大きい場面では、主担当が最上位のモデルにそれぞれ
独立に相談します。最上位のモデルを使うのは相談のときだけです。そのため、使用量の大半は安価なモデルの側に
収まり、重要な判断には最上位のモデルの意見が入ります。

この構成の `~/.severally/config.json` の例です。

```json
{
  "consultants": {
    "opus": { "cli": "claude-code", "model": "claude-opus-5-5" },
    "gpt": { "cli": "codex", "model": "gpt-6.1-sol" },
    "gemini": { "cli": "antigravity", "model": "gemini-4-argon-high" }
  }
}
```

モデルの ID は新しいモデルが出るたびに変わるので、使っている CLI に合わせて書き換えてください。`effort` を
書かなければ、相談相手は effort `high` で動きます。ただし Antigravity はモデル名で決まり（`gemini-4-argon-high`）、
`effort` を書くと設定の誤りになります。

そのうえで、主担当を安価なモデルで起動します（`claude --model sonnet`、動いているセッションなら
`/model sonnet`）。主担当は、[頼み方](../README.ja.md#頼み方)に挙げた場面で自分から相談します。「マージする前にみんなに
聞いて」のように頼むこともできます。相談相手は、それぞれの CLI のログインと利用枠を使います。

## APIの引数

`consult_start` の主な引数は次のとおりです。

- `context.expose_paths`: 相談相手に読み取り専用で写すファイルとディレクトリ（絶対パス）。git のリポジトリの中の
  ディレクトリは、git が一覧するファイル（追跡中のものと、`.gitignore` で外していない未追跡のもの）だけを写す
- `context.expose_diff`: `{ repo, base? }`。変更中の差分をブリーフに入れ、差分が触るファイルを写す
- `network`: `"off"` にすると、その回のどの相談相手も Web の検索と閲覧ができない
- `followup_to`: 追加の質問のもとになる答えの `job_id`。全員に聞いた相談の `group_id` を渡すと、全員にもう一度聞く。
  追加の質問はこれと `question` だけでよく、相談相手・モード・前の回の前提は、渡し直さなければそのまま引き継ぐ
- `retry_of`: 失敗したジョブの ID だけを渡すと、保存済みの問い・前提・network を使い、新しい相談として再実行する。
  ほかの引数は渡せない。成功した相手には再依頼せず、元の記録は残す。ファイルは現在の内容を写し直すが、保存した差分の
  抜粋は元のままなので、変更・削除の注記を確認する。問いや資料を変える場合は、新しく明示して相談する。認証や使用枠の
  問題は対処してから再実行する。設定した主モデル・CLI が変わった場合や、失敗時に代替モデルで動いた場合は拒否する。

`consult_list` は `target`、質問の部分文字列 `question`（大文字・小文字を区別しない）、`chain_id` で履歴を絞り込めます。
条件は `request` に包まずトップレベルで渡します。未知の引数は、条件を無視して一覧を返さないよう拒否します。
絞り込みは件数上限より先に適用します。`latest_completed_job_id` はその相談で最後に回答したジョブ、`rounds_remaining` は
後続の失敗も含めて使った回数を差し引いた残りです。複数の候補があれば内容を確かめてから続けます。
